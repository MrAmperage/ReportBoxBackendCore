# ADR 0011 — Независимый Auth

[Архитектура](../architecture.md) · [Auth API](../auth.md) · [RPC](rpc.md)

## Решение и мотивация

- Опциональный `auth.Module()` и обычный `NewValidator`: пассивные, без собственного listener, lifecycle, глобального состояния или обязательной зависимости от транспорта. Существующий RPC authorization hook достаточен, адаптер `auth/rpc` не меняет `rpc.Handler`.
- JWT с фиксированным issuer/audience/типом/асимметричным алгоритмом, обязательными `kid`, `sub`, `exp`; библиотека `golang-jwt/jwt/v5` вместо собственной криптографии, строгий ограниченный compact/JSON preflight. Ed25519 по умолчанию, RS256/ES256 опционально, без HMAC/none и token-supplied key URLs. Тип и алгоритм выбирает проверяющая сторона. Меньше рисков algorithm/key confusion и подмены refresh token.
- Два обязательных интерфейса KeyProvider/StateValidator: универсальный контракт, отсутствие зависимости от конкретных API, Protobuf, subjects, схем и модели прав AuthenticationService. Получение ключей и проверка текущего состояния раздельны. Неверифицированные claims не допускаются к state provider.
- `LocalPreferred` и `RemoteRequired`: скорость обычных запросов и строгий запрос к источнику истины там, где необходима более свежая проверка. При неизвестном состоянии fail closed. Синхронизация, кеш и remote fallback — ответственность специализированного AuthenticationClient, не Core. Ревизии состояния вместо хранения всех выданных Access Token. Достоверность локального кеша ограничена TTL, состоянием синхронизации и восстановлением; доставка событий не равна немедленному отзыву.
- Verified Identity с копиями mutable claims и производным context. Политики RPC перечисляются явно по procedure; неизвестные методы запрещены. Ресурсная авторизация остаётся прикладной. Ошибки возвращают безопасные коды; токены не логируются.
- `Revalidate` для длительной работы; stream auth hook при открытии не обеспечивает постоянный контроль. Отзыв после проверки не откатывает начатую операцию. Прикладные сервисы определяют повторную проверку/завершение потока и транзакционные гарантии.

Не реализуем в Core выпуск токенов, refresh, сессии, роли, permissions, централизованное хранилище, встроенный клиент конкретного AuthenticationService, кеш, NATS consumers для auth, автоматическую identity propagation, JWKS fetcher или service identity protocol. Эти решения остаются ответственностью потребителей, пока нет отдельной инфраструктурной потребности. [Auth API](../auth.md) определяет действующие ограничения и контракт провайдеров.
