# AGENTS.md

Инструкции для AI-агентов, работающих с репозиторием ReportBoxBackendCore.

## 1. Назначение и актуальный контекст

- Репозиторий: `MrAmperage/ReportBoxBackendCore`.
- Go module: `github.com/MrAmperage/ReportBoxBackendCore`.
- Проект — переиспользуемая библиотека для backend-сервисов ReportBox, а не самостоятельный сетевой сервис.
- Согласованный стек: Go, Uber Fx, ConnectRPC/Protobuf (Connect, gRPC, gRPC-Web), NATS/JetStream, net/http, pgx, slog, OpenTelemetry, Prometheus.
- UI-сервисы владеют сборкой микрофронтенда; Caddy раздаёт статику и проксирует разрешённые RPC. Не реализовывать frontend/REST server в Go. KrakenD исключён. Management опционален и закрыт.
- Проект развивается поэтапно. Не считать проектные API в документации реализованными. Фактическое состояние определять по текущей ветке и исходникам.

## 3. Правила реализации

- Следовать идиоматическому Go: gofmt, понятные имена, небольшие пакеты, явные ошибки и зависимости. Документировать экспортируемые API.
- Применять KISS, YAGNI, DRY и SOLID там, где это уменьшает сложность; не создавать абстракции и пустые пакеты заранее.
- Fx использовать в composition root и инфраструктурных модулях. Конструкторы прикладного кода — обычные Go-функции, без service locator и зависимости от контейнера.
- Core не открывает порты и не устанавливает сетевые соединения сам по себе. Инфраструктурные модули подключаются явно; обязательные зависимости проверяются.
- Не добавлять бизнес-логику, доменные модели, JWT-политику конкретного сервиса или UI-компоненты в BackendCore.
- Использовать нативные API выбранных библиотек. Не оборачивать каждый сторонний тип ради абстракции. Не добавлять новые зависимости без обоснования.
- Не добавлять второй обязательный RPC-стек поверх NATS. ConnectRPC — синхронные вызовы (Connect для browser, gRPC для Go как предлагаемый default), Core NATS — уведомления с допустимой потерей, JetStream — устойчивые события и задачи.
- RPC server на net/http, без универсального REST-фреймворка. Пакет `rpc` предоставляет независимо подключаемые server/client. Management listener отдельный. Статику раздаёт Caddy, не Go; UI deployment вне ядра.
- Сохранять совместимость публичного API после его утверждения; несовместимые изменения фиксировать явно. Точные версии Go и зависимостей брать из актуального `go.mod`, CI и утверждённых решений, не выдумывать их.

## 4. Lifecycle, надёжность и безопасность

- Валидация typed config до запуска. Некорректные явные настройки возвращают ошибку; не подменять их defaults молча.
- Библиотечный код не вызывает `os.Exit`, `log.Fatal` или `panic` для ожидаемых ошибок. Не изменять глобальный slog/telemetry state неявно.
- Сетевые ресурсы открывать в startup, возвращать ошибки bind/connect синхронно; при частичном старте освобождать выделенные ресурсы. Не открывать соединения и не запускать фоновые задачи в DI-конструкторах; см. уточнения в Core и ADR. Фоновые goroutines должны быть управляемыми.
- Не использовать startup context как lifetime context. Перед остановкой снять readiness, прекратить приём новой работы, завершить активную работу и закрыть зависимости с ограниченным deadline. Не полагаться только на порядок перечисления `fx.Option` или DI value groups. Учитывать границы гарантии Fx timeout и не обещать принудительную отмену произвольной goroutine.
- Liveness не зависит от доступности DB/NATS; readiness отражает состояние обязательных ресурсов. Не скрывать фатальные ошибки фоновых серверов.
- Для JetStream учитывать at-least-once, дубли, ack после устойчивого результата, ограниченные retries и идемпотентность. Не обещать exactly-once бизнес-эффекты или атомарность PostgreSQL + NATS.
- Разрешать через Caddy только публичные RPC; проверять авторизацию внутри сервиса. Management и внутренние методы не публиковать. Для RPC учитывать HTTP/2, limits, deadlines и drain streams. Для UI deployment исключать traversal, внешние symlinks и directory listing; не выдавать HTML вместо отсутствующего chunk. Не менять существующий Caddy/NaiveProxy без отдельной проверки.
- Не логировать токены, пароли, DSN, приватные payload и чувствительные заголовки. Не добавлять секреты в репозиторий. Не включать небезопасные настройки production без явного решения.
- Использовать context, deadlines и ограниченную конкурентность. Не игнорировать ошибки и не допускать утечек ресурсов.

## 5. Рабочий процесс агента

1. Изучить текущую ветку, затронутые исходники и документацию. При локальном доступе проверить `git status` и не затирать изменения владельца.
2. Определить минимальный объём задачи. Для существенных изменений кратко обозначить подход и архитектурные риски.
3. Выполнить изменения целиком в пределах задачи, без несвязанных рефакторингов. Добавить тесты на нормальный и ошибочный сценарии.
4. Обновить затронутую документацию. Этот файл обновлять только при изменении устойчивых правил работы, а не после каждой задачи.
5. Проверить изменения и сообщить, что реально выполнено: файлы, проверки, ограничения, непроверенные сценарии и принятые без явного согласования решения.

Не создавать отдельные логи разработки, временные отчёты или заглушки без необходимости. Не удалять чужие изменения, не менять историю Git и не включать в результат `.git`, секреты, кеши или сборочные артефакты без запроса.

## 6. Проверки

После появления Go-модуля и при изменениях исходников выполнять доступные и относящиеся к задаче проверки:

```sh
test -z "$(gofmt -l .)"
go test ./...
go vet ./...
go test -race ./...
```

Форматировать изменённые Go-файлы через `gofmt -w`. Проверять `go mod tidy` при изменении зависимостей и сохранять необходимые изменения `go.mod`/`go.sum`. Интеграционные тесты запускать по инструкции проекта с изолированными NATS/PostgreSQL и тестовыми настройками, когда соответствующие модули существуют. Для документации проверять ссылки и согласованность с ADR; не требовать Go-сборку от ветки без кода.

Не утверждать, что сборка, тесты или CI прошли, если они не запускались. Если проверка недоступна, указать конкретную причину.

## 7. Git и передача результата

- `Documentation` — первоначальная ветка спецификации. Не считать остальные названия веток утверждёнными, если владелец не определил их явно.
- По умолчанию изменения передаются владельцу в виде файлов или архива изменённых файлов с путями относительно корня репозитория.
- Владелец самостоятельно загружает изменения в GitHub. Не создавать ветки, коммиты, pull requests, теги и не выполнять push без отдельного явного указания.
- Не смешивать документацию с реализацией, если задача относится только к документации.
- Общение с владельцем и проектная документация — на русском; идентификаторы, код и стандартные технические термины — на английском.

## 8. Преемственность между диалогами

Репозиторий — единый источник актуального технического контекста проекта. Агент должен иметь возможность продолжить разработку по текущей ветке без доступа к истории предыдущих диалогов.

Перед началом задачи прочитать `AGENTS.md`, актуальные ADR, `docs/development.md` и профильную документацию, затем сверить их с исходниками, тестами и `go.mod`. Исторические ADR не считать текущими решениями, если их заменил более новый ADR. При расхождении документации с фактической реализацией явно обозначить его и устранить в пределах задачи.

После каждой задачи, включая частично выполненную, перед передачей результата:

- Актуализировать профильную документацию по фактически изменённому API, конфигурации, поведению, ограничениям и примерам использования.
- Отразить в `docs/development.md` текущее состояние этапа, завершённые и оставшиеся работы, ближайший следующий шаг, необходимые проверки и блокеры. Отличать написанный код от проверенного, а подготовленный архив — от опубликованной ветки. Не утверждать merge, release или прохождение CI без подтверждения.
- Фиксировать существенные архитектурные решения и их мотивацию в ADR; различать утверждённые решения, предложения агента и открытые вопросы. Не оставлять важные решения только в переписке.
- Указывать фактически выполненные проверки, их результат и причины невыполненных проверок; не переносить старый результат тестирования на изменённую реализацию без повторной проверки.
- Проверять относительные ссылки и непротиворечивость изменённых документов. Передавать изменённую документацию вместе с исходниками и тестами в том же архиве.

Поддерживать актуальное состояние, а не накопительный журнал: не создавать отдельные DEVELOPMENT_LOG, CHANGELOG или PROJECT_CONTEXT для передачи между диалогами. `AGENTS.md` хранит устойчивые правила, `docs/development.md` — состояние и план, профильные документы — действующие контракты, ADR — решения. README остаётся документом для людей. Если задача не меняет технический контекст, не переписывать документы ради формальной отметки. Публикация в GitHub остаётся за владельцем проекта.
